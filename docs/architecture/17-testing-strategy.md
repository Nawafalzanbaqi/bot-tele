# 17. Testing Strategy

The Foundation phase established the property that makes everything else
possible: **the entire suite runs with no database, no network and no Docker**.
That is not a convenience — it is what allows tests to be run on every save, and
tests that are not run are not tests.

This document extends that suite to cover the subsystems designed in Phase 02.

---

## 17.1 The shape of the suite

```
        /\          E2E / smoke        ~10   minutes   real Docker
       /  \         Performance        ~15   minutes   ARM64, nightly
      /    \        Chaos              ~20   minutes   nightly
     /------\       Contract           ~60   seconds   per adapter
    /        \      Integration       ~150   seconds   in-memory adapters
   /          \     Architecture       ~30   instant
  /------------\    Unit              ~800   milliseconds
```

Not a pyramid dogma — a cost/confidence ordering. Each layer answers a question
the layer below cannot, and none of them duplicate the layer below.

| Layer | Question | Runs |
| ----- | -------- | ---- |
| Unit | Are the rules right? | every save |
| Architecture | Are the boundaries intact? | every save |
| Integration | Do the parts compose? | every save |
| Contract | Do all implementations of a port behave the same? | every commit |
| Chaos | Does it recover? | nightly |
| Performance | Is it fast enough on a Pi? | nightly |
| Smoke / E2E | Does the real thing actually run? | pre-release |

---

## 17.2 Unit tests

**Scope:** domain rules, policies, planners, value objects, use case
orchestration. No I/O of any kind.

Obligations:

| Target | Obligation |
| ------ | ---------- |
| Every value object | Rejects invalid input; normalises; equality by value |
| Every state machine | **Every transition pair** tested: legal ones succeed, illegal ones raise |
| Every policy | Table-driven, one case per branch, including boundaries |
| Every use case | Happy path, each failure path, and the *events published* |
| `ProcessingPlanner` | The full decision matrix, including "undeliverable" |
| `RetryPolicy` | Backoff growth, jitter bounds, `retry_after` override |
| `CustodyPolicy` | **Every custody transition** — this is the product's central rule |

The exhaustive transition test is worth its weight: with 11 statuses, the table
is ~120 cases, generated by parametrisation, and it catches every
"I added a state and forgot a guard" bug for the life of the project.

Test doubles implement the same `Protocol`s as production adapters
(`FrozenClock`, `SequentialUuidGenerator`, `RecordingEventPublisher`,
in-memory repositories) so mypy checks them identically. Established in
Phase 01; extended with `FakeDownloader`, `FakeDeliveryProvider`,
`FakeWorkspace`, `ControllableQueue`.

---

## 17.3 Architecture tests

Executable enforcement of [04](04-dependency-graph.md). The full list is in §4.6.
The new ones for Phase 02:

- Context boundary matrix
- Third-party package placement
- **No foreign vocabulary** (`file_id`, `chat_id`, `ytdl`, `ffmpeg` outside
  their adapters)
- No module-level mutable state
- Every port has both a real adapter and a test double

These cost milliseconds and prevent the slow architectural decay that no code
review catches reliably at 6 p.m. on a Friday.

---

## 17.4 Contract tests

**The most valuable new layer in Phase 02.** One shared, parametrised suite per
port, which every implementation must pass — real and fake alike.

| Suite | Applies to | Asserts |
| ----- | ---------- | ------- |
| `RepositoryContract` | in-memory + SQLite repositories | Same ordering, same filtering, same pagination, same transactional semantics |
| `UnitOfWorkContract` | in-memory + SQLite | Commit persists; rollback discards; exception rolls back; nested use is refused |
| `QueueContract` | in-memory + SQLite | Exactly-once claim under concurrency; lease expiry reclaims; backoff honoured; cancellation observed |
| `DownloaderContract` | every downloader plugin | Cancellation ≤1 s; timeout honoured; errors classified; progress monotonic; no writes outside workspace |
| `DeliveryProviderContract` | every delivery provider | Receipt shape; ref reuse; error classification; capability honesty |
| `WorkspaceContract` | disk + tmpfs + fake | Containment; reservation accounting; idempotent release |

Why this matters: the in-memory adapters are what make the suite fast, and the
moment they behave differently from SQLite, **every test that uses them is
lying**. The contract suite is the mechanism that keeps them honest — and it is
the specific mitigation for the risk accepted in
[ADR-0005](../adr/0005-dual-persistence-adapters.md).

Some contract assertions (SQLite's `RETURNING`-based claim under real
concurrency) require a temporary file-backed database. That is acceptable:
SQLite needs no server, so "integration with the real database" costs
milliseconds and a temp file.

## 17.5 Integration tests

**Scope:** several real components composed, with in-memory adapters at the
edges.

| Test | Covers |
| ---- | ------ |
| HTTP surface, all endpoints | Status codes, problem documents, pagination, auth |
| Full pipeline with fake providers | Submit → download → process → deliver → **custody released** |
| Re-delivery path | Second request downloads **zero bytes** |
| Dedup at all three layers | URL, provider item, fingerprint |
| Cancellation mid-stage | Observed within one heartbeat; workspace cleaned |
| Retry and dead-letter | Backoff applied; DLQ populated; alert emitted |
| Telegram gateway | Update → command → reply, with a fake Bot API |
| Scheduler sweeps | Orphans deleted; leases reclaimed; jobs expired |

The pipeline test asserting **disk usage returns to zero** is the executable
version of the product's central requirement. If that test passes, the rule
holds; if it is missing, the rule is a comment.

## 17.6 Chaos tests

Nightly. Each answers "what happens when the Pi behaves like a Pi?".

| Scenario | Assertion |
| -------- | --------- |
| `SIGKILL` the worker mid-download | Job reclaimed ≤2 lease periods; resumed or restarted; no orphan after one sweep |
| `SIGKILL` between delivery and receipt commit | Delivery retried; at most one duplicate; **never lost** |
| `SIGKILL` between receipt and cleanup | Sweeper deletes bytes; custody correct |
| Fill the disk to 2% | Admission refuses; running jobs fail `TRANSIENT`; **no DB corruption** |
| Database locked for 10 s | Writers retry with backoff; no data loss; `busy_retries` metric rises |
| Provider returns 429 forever | Circuit opens; other providers unaffected; DLQ after max attempts |
| Clock jumps forward 1 day | Leases reclaimed once; no runaway expiry storm |
| Two schedulers started accidentally | Advisory lock prevents double-firing |
| Kill FFmpeg's child but not FFmpeg | Process group killed; no zombie; slot released |

These are the tests that justify the lease/checkpoint machinery. Without them,
crash recovery is a claim in a document.

## 17.7 Performance and capacity tests

Run on **actual ARM64 hardware** (or an emulated runner), nightly, with recorded
baselines. Regressions fail the build.

| Test | Target (Pi 4) |
| ---- | ------------- |
| API read p95, 2 jobs running | < 150 ms |
| Queue claim latency, 1 000 queued | < 10 ms |
| Job state transition | < 20 ms |
| Progress write amplification | ≤ 1 write/job/5 s |
| Memory, idle | api < 120 MB, worker < 150 MB |
| Memory, 2 GB download | worker < 250 MB (streaming, never buffering) |
| Full suite wall-clock | < 30 s |
| Backup + restore drill | < 60 s, integrity check passes |

The memory ceiling during a large download is the one that catches the classic
mistake of reading a file into memory to hash it.

---

## 17.8 Security tests

Mandatory, blocking. The corpora are listed in
[14](14-security-architecture.md) §14.13: SSRF, traversal, argument injection,
secret redaction, authorisation, size ceilings, rate limits.

These run as **unit tests** wherever possible (`UrlPolicy` and `FilenamePolicy`
are pure functions in the domain), which is precisely why those controls were
placed in the domain rather than in middleware.

---

## 17.9 Smoke and E2E

Pre-release, real Docker Compose, real SQLite, fake external providers.

| Check | |
| ----- | - |
| Stack starts, all healthchecks green | |
| Migrations apply from empty **and** from the previous release | |
| Submit → complete → local bytes gone | |
| Restart every container mid-pipeline; job completes | |
| `/metrics` and `/health/deep` respond | |
| Image runs on ARM64 | |
| Graceful shutdown drains within the grace period | |

**Migration tests deserve emphasis:** upgrade from the previous release's
database, assert data integrity, then downgrade. On SQLite, `ALTER TABLE` is
limited and Alembic must use batch mode ([20](20-architecture-decision-review.md)
§4.4) — a migration that works on Postgres can silently fail here, and the only
way to know is to run it.

No test ever hits the real Telegram API or a real content site. External calls
in CI are flaky, rate-limited, and occasionally a terms-of-service problem.
Recorded fixtures are used instead, refreshed deliberately.

---

## 17.10 Test data

| Kind | Source |
| ---- | ------ |
| Media samples | Tiny generated files (a 1 s black video, a 1 s silent audio) committed to the repo — kilobytes, not megabytes |
| Provider responses | Recorded JSON fixtures, sanitised, versioned |
| Database fixtures | Built through the domain (factories), never raw SQL inserts |
| Malicious payloads | Explicit corpora for the security suites |

Building fixtures through domain factories is a rule worth defending: raw
inserts can create states the domain considers impossible, and then tests pass
against data that can never exist — or worse, fail against data that can.

## 17.11 Coverage

| Layer | Target | Rationale |
| ----- | ------ | --------- |
| `domain/` | **95%+** | Pure logic, no excuses, this is the product |
| `application/` | 90% | Orchestration paths |
| `infrastructure/` | 70% | Adapters covered by contract tests |
| `presentation/` | 80% | Covered by integration tests |
| Overall | 85% | |

Coverage is a **smell detector, not a goal**. An uncovered branch is a question
("why is this unreachable?"), not a task to satisfy with a meaningless test.
Mutation testing on `domain/` (`mutmut`, weekly) is a better measure of whether
the tests actually assert anything, and is the recommended addition once the
domain rework in Phase 03 settles.

---

## 17.12 What is deliberately not tested

| Not tested | Why |
| ---------- | --- |
| Third-party libraries | yt-dlp's extractors are its own problem; we test our classification of its errors |
| Real network endpoints | Flaky, rate-limited, ToS-sensitive |
| FFmpeg's correctness | We test that we invoke it correctly and handle its exits |
| Every yt-dlp site | Impossible and pointless; the circuit breaker handles breakage at runtime |
| UI pixels | No UI yet; when there is one, behaviour over appearance |

Naming these prevents a slow drift into a suite that is slow, flaky and
distrusted — at which point the team stops running it, and the entire investment
is lost.
